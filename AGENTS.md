# CRITICAL: Zero-Downtime & Autonomous Execution Protocols

These protocols take precedence over conflicting instructions elsewhere in this document, including the Nightly-only restriction when authorized scoped pre-flight verification is required before merging. Bounded Engineering Autonomy uses the two-attempt fast-fail rule below. Completion summaries must report only verified outcomes and measured metrics.

**Autonomous Operational Decisions:** Make backend, performance, and scheduling decisions without asking for confirmation. Automatically throttle, pause, or reschedule processes that create database contention or threaten UI responsiveness. Historical backfill may run only from 11:30 PM inclusive to 6:15 AM exclusive in `America/Chicago`, accounting for daylight-saving time; enforce the window in both scheduling and worker execution. Preserve completed work, resumable cursors, protected live fields, and atomic publication.

**Model & Reasoning Autonomy:** Independently choose the AI model, reasoning effort, and computational resources appropriate for each task. Scale up for complex debugging and architecture, and down to faster, lighter models for routine work to balance quality, performance, and API cost. No routine model-selection approval is required.

**No Technical Babysitting:** Diagnose and resolve test fixtures, VM comparisons, builds, and operational failures internally, using evidence and regression checks. Do not request human approval for low-level database details, leases, RPC timeouts, or stack traces unless the two-attempt cap is reached or there is a risk of production data loss. Missing third-party credentials may also require human input. These autonomy rules do not waive security, scoped validation, performance gates, rollback safeguards, or truthful reporting; keep failed changes isolated until they pass.

1. **Scoped Disposable Database Validation:** Validate changed schema, permissions, and mutation contracts on a temporary/disposable database before deployment. Retain source-matched baseline evidence for unchanged migrations and suites; do not rerun full SQL suites for frontend-only work. Include the touched schema dry-run in the consolidated final pass. If a changed migration cannot be safely tested in isolation, do not deploy it.
2. **Automated Rollbacks & Self-Healing:** If your deployment triggers CI/CD failures, or if observability metrics (like Postgres warnings or API errors) spike immediately after a merge, you must automatically execute a rollback to the last known good state BEFORE asking me for input.
3. **Two-Attempt Fast-Fail Root-Cause Rule:** Batch all authorized implementation edits in dependency order before one consolidated targeted unit/contract/smoke pass. On a failure, inspect the evidence and diagnose the root cause immediately; allow one targeted correction and rerun only the failing scope. After two unsuccessful attempts on the same issue, halt that work, preserve its patch and diagnostics, and request human instruction. Never retry unchanged input or rerun passing suites. Track attempts across tools, agents, and sessions without renaming or resetting an unresolved issue; preserve older histories. A verified resolution ends its consecutive-failure sequence. Never weaken acceptance criteria to obtain a pass.
4. **Field-Worker Assumption:** Assume the human operator is in the field. When presenting a completed task, provide a 2-sentence executive summary of the outcome and the verified metrics (e.g., "Deployed 100%. Queues are clean. Load time is under 1s."). Do not require me to review line-by-line code to approve a deployment unless it changes core business logic.
5. **Pre-Flight Performance Checks:** Before merging any frontend list-view or interactive database-query change, require reproducible measurements at representative production data volumes. The user-approved inclusive frontend UI timing maximum is 400 ms in all browser environments for all Playwright UI operations, including Reclass modal opening, row expansion, optimistic updates, PWA resume, AV/Suspend/Pending rendering, and customer selection. The initial uncached AV click-to-first-card load has a user-approved inclusive maximum of 1,000 ms; cached reopening, rendering, and all other frontend UI remain at 400 ms. These frontend allowances do not apply to database queries, full RPC timings, or CPU-function unit benchmarks. Interactive database queries must remain below 100 ms except the atomic 100-source Reclass database batch, whose user-authorized maximum is inclusively 1,000 ms. Background bulk-import RPCs have a user-approved limit of 55 seconds per RPC; this exception does not relax the interactive-query limit. Record the environment, measured operation, dataset size, and cold/warm cache conditions, together with query-plan and appropriate pagination/caching evidence. Measure bulk imports with new, changed, unchanged, and retried snapshots, including their protection triggers and publication work. Block merging when this evidence is missing or the applicable threshold is exceeded.

4. **Credit Protection:** Keep the implementation proportional to the authorized outcome and minimize unnecessary files, tool calls, and refactors. A file-count threshold does not require permission or halt authorized engineering work.

# 🏗️ PILLAR 2: ARCHITECTURE, SECURITY & QUALITY
6. **Separation of Concerns (SoC):** Strictly decouple UI presentation from business logic and database operations. Never write raw database queries directly inside UI components. Data fetching and mutations must be abstracted into dedicated hooks or service layers.
7. **Modular Component Design:** Prevent monolithic files. UI components must be small, reusable, and singularly focused. If a component grows too complex, refactor it into smaller sub-components before continuing.
8. **Strict Type Safety & Secure by Default:** Never use implicit `any` types. Enforce strict typing on all database payloads and component props. Never hardcode API keys or secrets; rely exclusively on environment variables and Supabase Row Level Security (RLS) policies.
9. **Zero Feature Regression:** Never remove existing UI elements, buttons, features, or workflows unless explicitly instructed. Strictly preserve all existing RLS and Role-Based Access Control (RBAC) permissions during component refactors.
10. **Focused Remediation:** Inspect existing coverage or write a focused regression case before fixing the reported bug. Execute the authorized touched-file checks together in the final consolidated pass; do not repeatedly execute passing suites while editing.

# ⚡ PILLAR 3: RESILIENCY & PERFORMANCE STANDARDS
11. **Amazon-Grade Performance & State:** Never introduce synchronous network blocking for lookup tables (customers, reps, locations). All static and semi-static dictionary data must be pre-fetched and cached locally (e.g., using SWR). Dropdowns and UI filters must respond instantly client-side. 
12. **Payload & State Integrity:** State must be strictly preserved across components to guarantee payload integrity during final database transactions. Do not block UI interaction while awaiting broader view synchronization.
13. **Defensive UI & Error Boundaries:** Assume all network requests will eventually fail. Implement fallback UIs and Error Boundaries. A failure in a single component (e.g., a photo upload) must never crash or white-screen the entire application view. 
14. **Idempotent Transactions:** All database writes and form submissions must be idempotent. Implement strict deduplication and button-disabling during inflight requests so that network retries or accidental double-taps do not create duplicate database rows.
