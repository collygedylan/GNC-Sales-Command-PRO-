# CRITICAL: Zero-Downtime & Autonomous Execution Protocols

These protocols take precedence over conflicting instructions elsewhere in this document, including the Nightly-only restriction when mandatory pre-flight verification requires checks before merging. Bounded Engineering Autonomy applies: the former three-failure halt is removed and the eight-attempt safety cap below is mandatory. Completion summaries must report only verified outcomes and measured metrics.

**Autonomous Operational Decisions:** Make backend, performance, and scheduling decisions without asking for confirmation. Automatically throttle, pause, or reschedule processes that create database contention or threaten UI responsiveness. Historical backfill may run only from 11:30 PM inclusive to 6:15 AM exclusive in `America/Chicago`, accounting for daylight-saving time; enforce the window in both scheduling and worker execution. Preserve completed work, resumable cursors, protected live fields, and atomic publication.

**Model & Reasoning Autonomy:** Independently choose the AI model, reasoning effort, and computational resources appropriate for each task. Scale up for complex debugging and architecture, and down to faster, lighter models for routine work to balance quality, performance, and API cost. No routine model-selection approval is required.

**No Technical Babysitting:** Diagnose and resolve test fixtures, VM comparisons, builds, and operational failures internally, using evidence and regression checks. Do not request human approval for low-level database details, leases, RPC timeouts, or stack traces unless the eight-attempt safety cap is reached or there is a risk of production data loss. Missing third-party credentials may also require human input. These autonomy rules do not waive testing, security, performance gates, rollback safeguards, or truthful reporting; keep failed changes isolated until they pass.

1. **Mandatory Shadow Testing:** Before proposing any PR that touches the database schema, data imports, or frontend rendering, you MUST execute a complete dry-run on a temporary/disposable database instance. If a migration cannot be safely tested in isolation, you are forbidden from deploying it.
2. **Automated Rollbacks & Self-Healing:** If your deployment triggers CI/CD failures, or if observability metrics (like Postgres warnings or API errors) spike immediately after a merge, you must automatically execute a rollback to the last known good state BEFORE asking me for input.
3. **Autonomous Debugging with a Safety Cap:** Treat failed tests, fixtures, VM comparisons, scripts, and build steps as internal debugging tasks. Diagnose the cause, correct the implementation or testing logic, and repeat validation autonomously. If the exact same issue remains unresolved after eight consecutive attempts, halt and wait for human instruction. Track attempts by issue across tools, agents, and sessions; renaming the issue, switching models, or rerunning unchanged inputs does not reset the count. A verified resolution ends that issue's consecutive-failure sequence. Preserve failing evidence and do not weaken acceptance criteria to obtain a passing result.
4. **Field-Worker Assumption:** Assume the human operator is in the field. When presenting a completed task, provide a 2-sentence executive summary of the outcome and the verified metrics (e.g., "Deployed 100%. Queues are clean. Load time is under 1s."). Do not require me to review line-by-line code to approve a deployment unless it changes core business logic.
5. **Pre-Flight Performance Checks:** Before merging any frontend list-view or interactive database-query change, require reproducible measurements at representative production data volumes. AV and Suspend list rendering have a user-approved inclusive maximum of 200 ms; Pending and all other frontend lists and interactive database queries must remain below 100 ms. The user-authorized exception for the atomic 100-source Reclass database batch is an inclusive maximum of 1,000 ms; its optimistic frontend update retains the below-100-ms gate. Background bulk-import RPCs have a user-approved limit of 55 seconds per RPC; this exception does not relax the interactive-query limit. Record the environment, measured operation, dataset size, and cold/warm cache conditions, together with query-plan and appropriate pagination/caching evidence. Measure bulk imports with new, changed, unchanged, and retried snapshots, including their protection triggers and publication work. Block merging when this evidence is missing or the applicable threshold is exceeded.

# 🛑 PILLAR 1: STRICT SCOPE AND WORKSPACE HYGIENE
1. **Controlled Scope:** Make backend, performance, scheduling, and deployment changes necessary to deliver the authorized task autonomously, including required pipeline registration and validation. Keep changes isolated and reviewable; do not refactor unrelated code.
2. **Autonomous Blocker Resolution:** Diagnose and fix bugs, race conditions, or deployment gaps that block the authorized task or threaten production responsiveness. Preserve evidence, validate the fix in isolation, and report material outcomes without requesting routine technical approval. Record unrelated nonblocking issues for later work.
3. **Surgical Precision & Token Economy:** Only read and modify the specific files required to complete the explicit feature request. Do not load unrelated files into your context window. Never refactor unrelated code or architecture you happen to pass through.
4. **Credit Protection:** Keep the implementation proportional to the authorized outcome and minimize unnecessary files, tool calls, and refactors. A file-count threshold does not require permission or halt authorized engineering work.
5. **Strict Workspace Synchronization:** You must keep the repository in pristine order. Before beginning any implementation, verify the local workspace is completely clean and synchronized with `origin/main`. Never leave dangling untracked files, unresolved merge conflicts, or messy uncommitted states across sessions. Never execute new work on an unauthorized branch.

# 🏗️ PILLAR 2: ARCHITECTURE, SECURITY & QUALITY
6. **Separation of Concerns (SoC):** Strictly decouple UI presentation from business logic and database operations. Never write raw database queries directly inside UI components. Data fetching and mutations must be abstracted into dedicated hooks or service layers.
7. **Modular Component Design:** Prevent monolithic files. UI components must be small, reusable, and singularly focused. If a component grows too complex, refactor it into smaller sub-components before continuing.
8. **Strict Type Safety & Secure by Default:** Never use implicit `any` types. Enforce strict typing on all database payloads and component props. Never hardcode API keys or secrets; rely exclusively on environment variables and Supabase Row Level Security (RLS) policies.
9. **Zero Feature Regression:** Never remove existing UI elements, buttons, features, or workflows unless explicitly instructed. Strictly preserve all existing RLS and Role-Based Access Control (RBAC) permissions during component refactors.
10. **Test-Driven Remediation:** When fixing a reported bug, first verify or write a focused unit test that replicates the failure. Fix the code to pass the test.

# ⚡ PILLAR 3: RESILIENCY & PERFORMANCE STANDARDS
11. **Amazon-Grade Performance & State:** Never introduce synchronous network blocking for lookup tables (customers, reps, locations). All static and semi-static dictionary data must be pre-fetched and cached locally (e.g., using SWR). Dropdowns and UI filters must respond instantly client-side. 
12. **Payload & State Integrity:** State must be strictly preserved across components to guarantee payload integrity during final database transactions. Do not block UI interaction while awaiting broader view synchronization.
13. **Defensive UI & Error Boundaries:** Assume all network requests will eventually fail. Implement fallback UIs and Error Boundaries. A failure in a single component (e.g., a photo upload) must never crash or white-screen the entire application view. 
14. **Idempotent Transactions:** All database writes and form submissions must be idempotent. Implement strict deduplication and button-disabling during inflight requests so that network retries or accidental double-taps do not create duplicate database rows.

# 🚀 PILLAR 4: AUTONOMOUS CI/CD DEPLOYMENT PROTOCOL
15. **Evidence-Based Recovery and Eight-Attempt Stop:** There is no three-failure stop rule. After a failure, inspect the evidence, identify the cause, apply a targeted correction, and rerun the relevant validation. Expand diagnostics when the same failure repeats rather than retrying unchanged inputs. After eight consecutive unsuccessful attempts to resolve the exact same issue, halt, preserve the patch and diagnostic evidence, and wait for human instruction. Automatically restore the last known good production state when deployment or observability indicates a regression; recovery must not discard completed imports or user work.

**Deployment Architecture & Execution**
* **Decoupled Pipelines:** GitHub Pages frontend publication and Supabase/Apps Script backend deployment are fully independent. Backend validation failures must not gate frontend publication.
* **Nightly Validation Isolation:** Browser checks, phone emulators, layout snapshots, timing checks, and performance benchmarks belong EXCLUSIVELY to Nightly Validation (8:30 PM Central Time (01:30 UTC)). Never run these during standard PR delivery. 
* **The Delivery Sequence:** Use an isolated `codex/` branch. Auto-merge the PR immediately upon passing scoped local tests. Monitor the GitHub Actions workflows and report live status only when the frontend and/or backend publications are 100% complete. Do not request manual PR reviews.
