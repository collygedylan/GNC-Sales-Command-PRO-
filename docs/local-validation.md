# One local check for each change set

From the isolated feature checkout, install the lockfile dependencies with `npm ci` and prepare the release version before validation. Run `npm run test:select -- --json` to preview affected commands, then `npm run check:local` to execute them. The command runs the existing foundation check once, builds one complete site, deduplicates focused unit files and executes selected browser suites serially against that site. It does not dispatch CI. Subsequent edits require another local run; a clean commit alone does not change the source fingerprint.

## Build identity and evidence

The latest result is `.gnc-local/local-check.json`; each invocation also keeps an immutable report and separate logs under `.gnc-local/local-check-*`. Reports identify the base SHA, actual working-source digest, compiled-site digest, selected commands, unmapped files and per-stage durations. A working tree build must never be described as exact-commit release proof. Generated vendor/CSS outputs are rebuilt from pinned inputs and included in the artifact digest; all other tracked and nonignored untracked source bytes are included in the source digest.

The local browser adapter preserves each suite's tests and projects, supplies the fresh site explicitly, disables remote base URLs, refuses server reuse, and retains screenshots, traces and JSON results on failure. It never copies into or falls back to `_site`. Existing individual commands remain available; when reproducing a failed browser test against local evidence, supply `GNC_LOCAL_SITE_DIR`, `GNC_LOCAL_CONFIG` and `GNC_LOCAL_OUTPUT_DIR`, then use `playwright.local.config.ts`. For candidate reproduction, download and verify the failed run's sealed artifact and use its normal suite config. Keep the artifact SHA/digest and trace together.

## Selection and failures

The explicit map lives in `live-src/change-impact.json`. Selection includes the branch diff from `origin/main` plus working changes. A standalone repository without an `origin` remote uses HEAD and reports working changes only; an existing origin with no usable merge base stops selection and requires a fetch. Release-version-only substitutions and pinned generated build outputs do not select extra suites; any other edits in those release-marker files still count. The source fingerprint still includes release versions. Foundation always runs, even when no feature maps. Known module edits select their contracts and relevant browser suites; shared or unknown edits include startup and Request/account boundary checks. Documentation edits need only the baseline. Unknown coverage is printed; add a mapping and focused regression for a new feature instead of treating the baseline as complete feature coverage. Database/functions and broad performance validation remain in their isolated candidate jobs.

A failed build or baseline stops focused execution. Any failed stage leaves the latest local result unsuccessful, preventing `release-candidate.mjs prepare --dispatch`. The guard also rejects source edits and changed/missing artifacts. It does not replace exact candidate proof or change the `prepare`, `check`, promotion or production-health interfaces. The existing complete candidate and hosted gates remain required.

Read the one failing stage's log/trace first. Record app defect, fixture/test defect, build/artifact mismatch or runner/infrastructure once evidence establishes the cause; an unclassified timeout is not automatically a flaky test. Do not add blanket retries or remove assertions. Reproduce only the failed case against the identified build. Preserve the first failure, diagnose a correction, then use at most one corrected candidate validation.

The prior Bunch Notes iPhone failure (candidate `8e9e375`, run `36287893736`) contained the completed location data and visible parent card; a mouse click reported success without opening its child card. The focused correction waits for completed-queue readiness, uses touch input on mobile, and asserts the parent-to-child transition. Repeated focused reproduction is justified for this observed failure, not a default for every edit.

## Three-change measurement

`npm run ops:record -- validation-report` lists local baseline, build and focused durations, selected suites and source identities from the existing operations ledger directory. The quiet release watcher adds the candidate SHA, outcome and elapsed time from workflow creation to the last completed job when GitHub supplies those timestamps; unavailable timing stays null. Compare three distinct completed changes, not three reruns of one change. Keep account usage snapshots with the normal phase ledger; local test execution time is not model token usage. Use `scripts/report-release-timings.mjs` for detailed candidate/hosted timings. Review redundant local coverage after those three changes; do not remove any required candidate/live gate to meet a time target.
