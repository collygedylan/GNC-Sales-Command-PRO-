# Protected releases and bounded incident recovery

All changes use the canonical GNC repository and an isolated worktree from fetched live `origin/main`. Preserve diverged local branches and unfinished work; do not reset them. Production is a deployment target, never a development sandbox. Open new Codex tasks in the canonical project/worktree so scoped permissions and project defaults apply; changing a terminal directory does not change an existing task's model or permissions.

## Development isolation, without paid hosting

- Install locked dependencies and compile the current source with `npm run build:live`. `npm run preview:isolated` serves that compiled shell on `127.0.0.1:43117`, with remote API connections, forms, frames and service workers blocked by response CSP. Existing synthetic fixtures remain available. It deliberately does not read production data or silently emulate a logged-in production account. Configure local/fixture data for the view under test.
- Database/functions validation uses the existing isolated Supabase CI stack, local migrations and fixtures. On machines with Docker, use the same prepared migration project and `supabase db reset --local --no-seed`; never substitute `--linked`, a production URL or production credentials. Docker is not installed on this workstation; the isolated CI lane is therefore required. Do not install paid hosting.
- Run **Provision isolated GNC test resources** on validated current main once, and after sandbox source needs refreshing. It uses the existing protected Google credential to create/reuse a separate marked Apps Script project and per-type test folders. It does not copy production Script Properties, create production triggers or expose a public web app. Only sanitized counts/status are uploaded; raw configuration stays local to the runner. Interrupted folder provisioning resumes by marker; unrelated projects/folders are never adopted or deleted.
- Generated Apps Script test source remaps known folders, intercepts email without sending it, blocks arbitrary HTTP, advanced Drive, spreadsheets and scheduled triggers. Run pure logic/integration fixtures locally and in CI. Google authorization may still be needed for interactive execution of the new project. A blocked service is an explicit unsupported test operation, **not a successful end-to-end import test**. Cloud Apps Script cannot reach a workstation's localhost database; this zero-cost setup does not reproduce cloud performance or every external conversion path.
- Never deploy generated sandbox source to production. Production jobs require main; Apps Script additionally verifies exact-current-main candidate proof, the pinned public deployment ID, and Google's project/deployment ownership before any content update. Keep `APPS_SCRIPT_PRODUCTION_DEPLOYMENT_ID` pinned; the optional script-ID variable adds another check. These guard trusted workflows against accidental use; repository administrators can still change workflow policy.

## Incident procedure and diagnostics

Run `npm run ops:diagnose` first. It makes bounded HTTP reads and a database `BEGIN READ ONLY` transaction with an eight-second statement timeout, always rolled back. It reports exact live versions, dataset readiness, recent import states, last successful import, migration digest and sampled API latencies. It never runs imports, sends email, advances outboxes or changes readiness. Service availability probes are not tests of a real user's authorization.

Use existing protected environment inputs: `GNC_SUPABASE_DB_URL`, optional `GNC_SUPABASE_CA_FILE` (defaults to the bundled official public Supabase CA; certificate verification stays enabled), `PRODUCTION_SUPABASE_SERVICE_ROLE_KEY`, and optional app/Apps Script overrides. Missing credentials and failed TLS are reported as unavailable—not healthy or an application outage. Do not put keys in source, command text, screenshots or reports. `--save` retains a sanitized report under ignored `.gnc-local`. See [Supabase certificate guidance](https://supabase.com/docs/guides/platform/ssl-enforcement).

Import retries retain eight deduplicated metadata-only failures in `MANUAL_SYNC_FAILURE_HISTORY_V1`; editor function `getManualSyncImportDiagnostics_()` provides sanitized stage/code/time within seven days. Public deployment health exposes only aggregate counts/activity, not filenames, users or error bodies. Diagnostic reads never mark a stale import complete or clear a fence.

Within ten minutes without a clear cause, reassess the evidence and escalate the narrow hard problem. At thirty minutes report restoration or a precise blocker and next action. These are incident checkpoints and routine-fix targets, not promises that complex work or full validation fits that duration. Restore service before unrelated feature changes. Stop repeating an unexplained failure.

## Recovery bundle and promotion

After exact-live checks pass, retain the candidate proof, sealed site artifact, sanitized Apps Script recovery evidence from its sync workflow, current diagnostic JSON and recovery bundle outside Git. `node scripts/recovery-bundle.mjs capture PROOF_JSON SEALED_SITE HEALTH_JSON SCRIPT_EVIDENCE_JSON` verifies the artifact and binds matching frontend/script commits, the authoritatively verified deployed script version, and exact database migration digest. Save its output in the private release report directory. `rehearse BUNDLE_JSON SEALED_SITE CURRENT_HEALTH_JSON` verifies a recovery candidate without deploying or writing business data. Missing/expired artifacts or any migration-state difference block automatic recovery until compatibility is explicitly established.

The bundle is evidence, not a bypass token. A rollback still follows the existing exact-commit release workflow: restore compatible source on a new branch, validate, and promote its sealed artifact. Never restore an old database snapshot over business transactions. Keep source/artifact copies outside retention-limited CI storage if long-term recovery is needed. A rehearsal does not claim users have run the rollback in production.

For normal changes: focused freshly compiled regression, bounded review, seal commit, `prepare --dispatch`, quiet watcher, exact `check`, current read-only health, normal fast-forward main promotion, and all exact-live checks. Reuse passing results only while the commit and relevant configuration are unchanged. Compatible backend support precedes frontend dependencies; destructive schema changes and new spending are separate approvals. A failed candidate leaves live production unchanged. Routine successful releases within an authorized implementation task do not need another permission question.

## Time and usage evidence

Follow `model-routing.md`; do not silently claim an existing owner changed models. Project defaults apply only when supported/loaded, and explicit app choices take precedence. Use one bounded specialist when useful, never a fleet of duplicate investigators.

`npm run ops:record -- diagnosis MODEL EFFORT [USED_PERCENT]` appends a local event. Record `implementation`, `validation`, `deployment`, `verification`, then `complete` or `blocked`; `npm run ops:record -- report` summarizes elapsed phases. Capture the actual available model/effort and usage, or `unavailable`. Track the next three changes and compare successful completed fixes. Account allowance deltas include other tasks and reset effects; they are not exact billing or promised savings.

No extra paid hosting, global account changes, automatic worktree cleanup, skipped safety suites, or business-data restoration is authorized by this protocol.
