# Sales/mobile release acceptance inventory

This is a source-derived coverage inventory for the current GNC application, independent of the Windows Server copy. It records existing test implementations and missing acceptance evidence. It is **not a passing test report**. The initial inventory was prepared by source inspection. Subsequent diagnostic browser results are recorded separately below; no production operations or deployments were executed for this inventory. The release owner must attach results for the exact compiled commit and artifact; a test file's existence does not establish a pass.

Inventory sources: `index.html` primary `view-*` containers, `ROLE_ACCESS_VIEWS`, `TRACKED_VIEW_IDS`, Manager module options, Tasks options, detail tabs, dialog IDs; `assets/sales-workspace.js`, `assets/navigation-preferences.js`; browser configs and the release workflow. `view-wrapper` is structural, not a functional module. Building has no retained dedicated primary view and must remain absent from navigation; its underlying records are not removed.

## Evidence classes and gaps

- **C**: browser test implementation exercises the compiled shell, with isolated fixture transport or a mutation-blocked identity. It establishes only its stated UI/transport assertions.
- **B**: browser test implementation exists, but may inject state/functions or use a dedicated fixture. Read the named scenario before treating it as full compiled-app coverage.
- **D**: SQL or local-Supabase integration test implementation exercises database functions/policies. Single-session stale/replay assertions are not simultaneous-transaction tests.
- **U**: unit, API adapter, parser, or source-contract test implementation. It does not establish browser usability or deployed backend behavior.
- **G**: no dedicated primary-workflow browser coverage located. Shared Home/permission/refresh tests are listed only as partial evidence.
- **Deferred**: expressly excluded functionality: Can Filling and Order Pulling. Visibility, explanatory text and absence of misleading action controls still require validation.

All rows below have execution status **Unrecorded for this release** until the release owner supplies a commit/artifact-linked result. Gaps apply even when some implemented tests pass.

| Gap | Missing evidence and required closure |
|---|---|
| G1 | Execute the named scenario against the exact fresh artifact; record project, commit, digest, result and log/trace. Do not infer success from an earlier release. |
| G2 | Exercise the module's primary action through confirmed save, reload, failed save, permission denial and reconnect. Opening a tile or stubbing a renderer is insufficient. |
| G3 | Cover 320px through large phones, landscape/tablet, every supported theme, keyboard overlap, 44px targets, horizontal overflow, footer spacing and Back retention in this specific screen/dialog. Shared CSS is not evidence. |
| G4 | Exercise real authenticated API/database/storage calls in an isolated environment, including two competing sessions, stale/disabled identities and direct unauthorized access. Deterministic browser routes do not prove backend isolation. |
| G5 | Record physical Android/iPhone camera, file-selection, installation, keyboard, background-resume, offline/reconnect and service-worker-update evidence separately from browser emulation. |
| G6 | Verify generated PDF pages/content, protected attachments, frozen recipients and real isolated delivery failure/acknowledgement-loss recovery. Stub PDF/email responses do not prove delivery. |
| G7 | Compare effective access for existing users before/after and prove live grant refresh across separate authenticated sessions, including Reports-only exceptions and protected actions. |

## Release lane selection and limitations

The current `.github/workflows/release-validation.yml` implements these lanes; none is marked passed here:

- **Unit:** `scripts/run-release-unit-checks.mjs` combines explicit new Sales/navigation/production tests with package `test:photo`, `test:pilot`, `test:live-sync`, and release tests. It is not an unrestricted glob of all `tests/*.test.mjs`; Python weather tests are not automatically included. `npm run test:v2` is separate.
- **Functional browsers:** `playwright.release-functional.config.ts` inherits the explicit `playwright.config.ts` test-match regex, with four shards. It includes responsive/Eval/Block Clearing/Photo History/marketing suites. A newly added arbitrary browser file does not enter this lane automatically. Many scenarios inject state and some use `/tests/fixtures/ops-precision-browser.html`; classify them as B, not authenticated end-to-end proof.
- **Compiled browsers:** explicit configs for footer, Home/startup/verified loading, Season, Suspend, Docks, AV Blanks, session recovery, AssignedTo, verified cache, Request reliability/photos, Bunch, Sales mobile, app-wide module mobile, HL/Restocking and stable refresh. Sealed `_site` is downloaded and verified after tests. `playwright.sales-mobile.config.ts` defines Desktop Chrome, Pixel 7, iPhone 13/WebKit and 320px profiles; light/dark layout checks cover its scenarios only.
- **Timing:** isolated scroll/login-photo and Android startup/photo lanes. Timing results do not validate all business workflows.
- **Database:** `.github/workflows/release-database.yml` assembles selected migrations/fixtures/SQL tests, starts isolated Supabase, applies migrations, runs pgTAP, native request/provisioning browser integration and Deno function tests. Sales, navigation and production SQL acceptance files are explicitly wrapped without suppressing assertions. The combined `supabase/ci/sales_mobile_pglite.mjs` is useful local SQL evidence when run, but is not hosted Supabase/Storage/Edge or multiple simultaneous sessions.
- **Service worker:** `tests/service-worker-isolation.e2e.spec.ts` has `playwright.sw-isolation.config.ts`, but that browser config is not present in the inspected release-validation compiled matrix. Most browser profiles explicitly block service workers. The unit isolation test is included; it cannot establish install/update/offline/background behavior.
- **Production canary/health:** `tests/production-request-canary.spec.ts` with `playwright.production.config.ts` is a separate, mutation-blocked live canary. Optional `production-health` is a read-only probe. Neither proves protected production mutations, real mail delivery, or physical mobile behavior.
